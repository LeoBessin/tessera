# Roadmap

From the current walking skeleton to a finished fifteen-hour co-operative
campaign.

Each phase states what "done" means in terms a test can check. Phases are
ordered by dependency, not by appetite: phase 1 comes first because nothing
downstream of it is meaningful until identity is real.

Read `CLAUDE.md` for the working rules and `docs/adr/` for why the
architecture is the way it is. The premise, the art direction, the trades and
the detail mandate are ADRs [5](docs/adr/0005-the-mosaic-premise.md),
[6](docs/adr/0006-colour-is-the-progress-bar.md),
[7](docs/adr/0007-three-trades-and-per-role-unlocks.md) and
[8](docs/adr/0008-generated-art-must-be-detailed.md).

---

## The game, in a paragraph

The world was a single mosaic and it has been broken apart. Players are
**restorers** — craftspeople who arrived to re-lay it — working in parties of
two to four. A chapter is a **panel** of the mosaic, and restoring a panel
reveals what it depicts, so repairing the world and learning its story are the
same act. Opposing the work are **scavengers**, pulling the mosaic apart for
their own purposes. The register is quiet and melancholy. Restored panels
regain colour; unrestored ones stay cold, which makes fifteen hours of progress
visible by looking around rather than by opening a menu.

Every asset is generated by code, and ADR 8 holds generated work to the same
standard as made work: restraint in what is included, craft in how it is made.

## Phase 0 — Foundations · **done**

The walking skeleton, verified end to end.

- Pure, dependency-free simulation (`packages/sim`) — 84 tests, 98% coverage
- Authoritative Colyseus server at 30 Hz with client-side prediction running
  the *same* `applyInput`
- Isometric Three.js renderer under an orthographic camera, procedural geometry
  — currently primitives, which ADR 8 classifies as placeholder rather than style
- Keyboard-only input modelled as intents
- Per-player progression with a property-tested monotonicity invariant, now
  branching per trade
- Replay-digest regression gate, architecture boundaries enforced in CI
- Both Docker images build, run and report healthy

Players can connect, move, be downed and revive. There is no combat, no
content, and no identity.

## Phase 1 — Google sign-in, required to play

**The game is not playable without a connected Google account.** There is no
anonymous path, no guest mode, and no local-only fallback.

This phase comes first because progression is currently keyed on
`client.sessionId` — a value thrown away when the socket closes. Every hour of
campaign built before identity is real is an hour of progress that cannot be
saved to anybody.

### Work

- Add `@colyseus/auth` and register Google as an OAuth provider:
  `auth.oauth.addProvider('google', { key, secret, scope: ['openid', 'email', 'profile'] })`
- Add a `static async onAuth(token, options, context)` to `CampaignRoom` that
  calls `JWT.verify(token)` and returns the payload. An unverified token must
  throw, and the join must fail — not degrade to a guest.
- Derive the player identity from the Google subject claim (`sub`), which is
  stable, unique, and never reassigned. **Do not key on email**: people change
  theirs, and that would silently orphan a campaign.
- Replace the `?? client.sessionId` fallback in `CampaignRoom.#playerIdOf` with
  the verified identity. The fallback must be *deleted*, not left unreachable.
- Client: a sign-in screen owned by a new `apps/client/src/auth/` module. The
  canvas does not mount until a session exists.
- Token lifecycle: storage, refresh before expiry, sign-out, and a clean
  reconnect when a token expires mid-session.
- Party invites: a room code or invite link, so friends can reach each other's
  sessions now that rooms are tied to accounts.

### Guard rails

- Identity is **only** ever derived from the verified JWT on the server. A
  `playerId` arriving in a join payload is ignored. Add a test that a forged
  identity in room options does not influence which save is loaded.
- Store the minimum: Google subject, display name, avatar URL. Nothing else.
- Keep `packages/sim` untouched. Authentication is a server adapter concern and
  must not reach the domain — `pnpm arch` will enforce this.

### Needs a human (cannot be AI-managed)

Create the OAuth client in Google Cloud Console: a project, an OAuth consent
screen, a Web Application client, and authorised redirect URIs for both
`http://localhost:2567` and the production domain. Then supply
`GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` as Coolify secrets.

### Done when

A restorer with a Google account can sign in, play, close the browser, sign in
again days later and resume at their own checkpoint. A player without one
cannot join at all, and the refusal is legible rather than a hang.

## Phase 2 — Durable progression

Identity is stable, so progress can finally outlive a process.

- Postgres via Drizzle; schema as plain TypeScript so migrations are reviewable
- `PostgresProgressionRepository` behind the existing
  `ProgressionRepository` port — the room does not change
- The schema must represent **three unlock sets per player**, one per trade.
  This is the only place ADR 7 reaches outside the domain, and a schema that
  flattens them back into one list silently reintroduces the bug that ADR
  replaced.
- Save on checkpoint as well as on leave, so a crash costs one room rather than
  a session
- `mergeProgression` on reconnect, so a conflict resolves upward and never
  destroys progress — including the union *within* each trade, which already
  has a test
- Postgres service added to `docker-compose.yaml`

**Done when** killing the server mid-session loses no progress beyond the last
checkpoint, in any trade, proven by an integration test rather than by
inspection.

## Phase 3 — The three trades and the first panel

The first genuinely playable slice, the first real exercise of the netcode, and
the first time the premise is visible rather than merely written down.

### The trades

Three roles, chosen per session, separated by how they act on the world rather
than by damage numbers:

| Trade | Acts by | Wants |
| --- | --- | --- |
| `cutter` | removing what is in the way | openings, angles, space |
| `setter` | putting the mosaic back | time, and someone buying it |
| `keeper` | holding a place steady | a place worth holding |

The combat design rests on these combining — one restorer setting up what
another completes. A trade that is satisfying to play alone is a trade that has
failed its brief.

### Work

- Abilities on cooldown per trade, driven by the existing intent model so
  rebinding stays a data change
- Scavengers as the opposition: behaviour in `packages/sim`, deterministic and
  seeded — never `Math.random`
- Damage, downing and co-operative revival, extending what phase 0 already has
- Hit resolution through `allowRewindState` lag compensation, so a hit that
  looked fair on the attacker's screen resolves as one
- Dash on the existing `dash` intent, with a cooldown
- One complete panel: arrival, checkpoint, the scavengers already at work, the
  restoration, the reveal of what the panel depicts
- **The first detailed generators**, replacing placeholder primitives for
  everything this panel contains: the tesserae themselves, the restorers, the
  scavengers. Judged across seeds rather than at a seed — a generator that
  looks good once has not been shown to work.
- A loading state, which the game does not currently have and which generation
  time now requires

### Done when

Two restorers in different trades can clear a panel together, neither could
have cleared it alone, and a new replay fixture covering combat holds its
digest. No primitive placeholder remains in anything the panel shows, and
generation leaves the simulation's PRNG untouched — proven by the digest, which
must not move when the generators change.

## Phase 4 — The content pipeline

The phase that decides whether fifteen hours is achievable or merely intended.

- Panels as **validated data**, not code, in `packages/content`
- Zod schemas for every content type, named in the vocabulary of the fiction —
  panel, tessera, scavenger, trade — because a schema that names things the way
  the game does is one fewer translation layer for whoever writes the twelfth
  panel
- Each panel declares both its states: what it looks like broken and what it
  looks like restored. ADR 6 makes `PALETTE` content rather than a constant in
  `scene.ts`, and this is where that move belongs.
- Panels declare their subject as **parameters to a generator**, not as
  geometry. Content says what a panel depicts and how densely it is laid; the
  renderer's generators turn that into tesserae. This is the division that lets
  content stay authored data while the art stays code.
- A graph validator run in CI: every panel reachable, no soft-locks, every
  required ability obtainable before it is required — **checked once per
  trade**, not once overall, which is the cost ADR 7 knowingly accepted
- A pacing budget per panel (estimated minutes), summed and asserted against
  the fifteen-hour target

**Done when** a panel can be added, validated and played without a single
change to `packages/sim`.

## Phase 5 — The campaign

Build out roughly twelve to fifteen panels to the fifteen-hour target.

- Difficulty and ability unlocks paced across three trades, not one
- The restored mosaic read as a whole: the panels are one image, so their order
  and their subjects have to add up to something
- Colour returning as panels are restored, per ADR 6 — sparing, not opulent.
  Restoration means resolution rather than richness, and players must remain
  the most saturated thing on screen.
- Instrumentation: time-to-complete and deaths per panel, to find the panels
  that are actually too hard rather than the ones that feel it
- A generation budget held across twelve to fifteen panels: instance counts,
  load time and session memory. If runtime generation stops being affordable,
  ADR 8 names build-time baking as the known escape hatch rather than a
  surprise.
- Audio, synthesised through the Web Audio API to match the procedural art
  direction and keep the zero-asset pipeline. Sparse and tonal, with long
  silences; a dense score would contradict the picture.
- Accessibility: full key rebinding (already a data change), adjustable text
  size, and a colour-blind-safe palette that **must still distinguish restored
  from unrestored without relying on hue** — progress encoded as saturation is
  progress some players cannot see

**Done when** a playthrough lands within 13–17 hours and no panel is a
measurable outlier for deaths.

## Phase 6 — Production

- Deploy to Coolify from `docker-compose.yaml`; `wss://` throughout
- Structured logging, error reporting, uptime and room-count metrics
- Load test: how many concurrent parties does one container actually hold?
- Add `RedisPresence` and `RedisDriver` **only** once that number is the
  binding constraint — it is a two-line change and costs nothing to defer
- Backups for the progression database, with a restore that has been rehearsed

---

## Cross-cutting, every phase

- Test first. In `packages/sim` the code is pure, so there is no excuse.
- Property-test anything that must hold for *all* inputs, not for three
  remembered examples.
- Add a replay fixture whenever a new system changes how the game plays.
- Never bless a replay digest to turn a build green without knowing why it
  moved.
- `pnpm verify` passes before anything is called done.

## Open threads

Decisions deliberately deferred rather than forgotten.

| Thread | Where it was left |
| --- | --- |
| Players render as an octahedron, which ADR 5 does not explain for craftspeople with a trade | Either the form changes when facing exists, or the fiction grows a reason |
| Three trades is a bet that three combines richly enough for fifteen hours | Revisit after phase 3 playtesting, before phase 5 commits content to it |
| How a panel's subject is actually drawn — the mosaic imagery itself — is answered in principle by ADR 8 (instanced tesserae, generated in detail) but unproven | First real test is phase 3's single panel; if detail cannot carry depiction there, phase 4's schema is built on sand |
| Whether detailed runtime generation is affordable in a browser tab | Measured in phase 3, budgeted in phase 5; build-time baking is the recorded fallback |
